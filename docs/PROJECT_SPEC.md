# GPU 集群管理接口平台：项目开发说明

文档状态：开发基线草案。业务范围来自需求讨论；下文标为“建议”或“待确认”的内容不是已验收事实。

## 1. 项目目标与已确认需求

建设独立于 Mini Token Factory 的管理接口平台。上游系统通过接口上传镜像、要求平台分发镜像并启动容器工作负载、查询运行状态和执行节点管控。

已确认：

- 目标硬件为 64 台服务器、共 512 张 NVIDIA B300 显卡，型号统一。
- 用户要求负责集群相关建设与运维，而不只是调用已有集群。
- 平台负责镜像接收、版本记录、分发和工作负载启动。
- 对接方式为上游调用接口；不需要管理前端、聊天页面、模型路由或推理业务负载均衡。
- 业务存在长连接，但具体协议、持续时间及会话恢复能力尚未确定。
- 新项目独立开发；Token Factory 仅作为后续可部署的测试应用。

规划假设：每节点 8 卡。总量支持这一平均值，但必须用资产清单确认实际分布。不能由 B300 型号推断整机型号、互联带宽、操作系统或驱动版本。

## 2. 范围与职责边界

主层 L5 容器与调度层；管理接口与权限属于 L8；依赖 L4 驱动与加速运行时和 L1–L3 硬件、互联、网络与存储。

### 2.1 必须交付

1. 上游管理接口：调用方认证、资源权限、参数校验、幂等和异步操作查询。
2. 镜像：上传授权、仓库核验、版本目录、按 digest 引用、删除约束。
3. 分发：部署时按需拉取；显式指定节点的预热及逐节点结果查询。
4. 工作负载：创建、查询、启动/停止、扩缩容、版本更新、删除和明确的访问方式。
5. 节点：清单、健康、GPU 资源分配、标签、停止/恢复调度、受控排空。
6. 集群生命周期：安装基线、节点纳管、升级、证书、备份恢复和故障维护流程。
7. 运行保障：管理服务、仓库、数据库、集群组件的健康指标、操作日志及最小必要告警。

节点重启、下电、重装属于总体运维责任，但必须确定带外管理协议和操作规程后实现适配器；不能伪装成普通 Kubernetes 操作。

### 2.2 不包含

- 推理 API、模型选择、Token 计费、聊天、学习页面、业务会话代理。
- 自研 Kubernetes 调度器、镜像存储引擎或 GPU 驱动。
- 第一版的 GPU 虚拟化、显存切分、跨机联合训练调度、自动性能优化。
- 第一版的任意 SSH 命令、任意 Kubernetes YAML、容器终端接口。

“不包含推理路由”不等于忽略工作负载可访问性。平台必须返回约定的服务访问地址，且标明内部/外部范围。

## 3. 系统结构与建议技术方案

```text
上游系统
 ├─ HTTPS 管理 API → Java 管理服务 → PostgreSQL
 │                              ├─ 操作执行器 / 状态协调器
 │                              ├─ Kubernetes 适配器 → API Server
 │                              ├─ 仓库适配器 → Harbor
 │                              └─ 节点生命周期适配器 → 自动化工具 / 带外管理
 └─ 标准镜像推送 → 镜像仓库 → 节点容器运行时
                                      ↓
                             GPU 工作负载实例
```

建议首版：Java + Spring Boot、PostgreSQL、Kubernetes Java 客户端、Harbor、containerd。Java 服务按模块组织，API 与后台执行器可使用同一代码库、不同进程角色；不先拆成大量微服务。具体受支持版本在环境盘点后锁定，不使用浮动 latest 作为生产依赖。

平台负责业务对象、规则、编排和状态；Kubernetes 负责工作负载编排与节点放置；节点运行时负责真实拉取和启动；仓库负责保存镜像层。GPU 的资源发现与运行支持通过兼容的 NVIDIA 组件提供。

数据库不是集群实际运行状态的唯一真相：保存期望配置、操作记录和带时间戳的观察结果。Kubernetes/仓库失联时标记 Unknown/Stale，不能把旧缓存当作当前健康状态。

首期使用单集群进行验收，数据模型保留 cluster_id。是否生产多集群待确认，不预先假定 64 台全在同一机房。管理与控制平面需要独立且高可用的基础设施资源，是否有额外通用服务器待确认。

## 4. 镜像接收、版本与分发

### 4.1 建议默认流程：标准镜像推送

1. 上游申请上传会话，指定项目、仓库名和 tag。
2. 平台返回受限上传目标、过期时间和上传授权方式。
3. 上游按标准 Registry 接口推送镜像层与 manifest；大文件不经过 Java API 缓冲。
4. 上游提交完成确认，平台向仓库核验 manifest、digest、平台架构和可访问性。
5. 平台登记 Available 镜像，返回 image_id。所有部署把 image_id 解析为不可变 digest。

OCI（开放容器倡议）定义容器镜像相关规范。标准推送兼容客户端需以所选仓库实际支持能力验收。不得在收到 complete 请求后仅凭上游提供的 digest 就认定成功。

上传凭据使用短期、最小仓库范围权限；与节点拉取凭据分开。禁止把管理员凭据返回上游。仓库支持范围和有效期的机制在适配器实现时验证。

tar 文件导入是待确认扩展，不在首版默认实现；不得自动导入宿主机容器环境。

### 4.2 版本模型

tag 是可变名称，digest 才标识具体内容。镜像记录保存解析结果；上游覆盖 tag 不改变已部署实例的目标镜像。

区分“删除平台记录/撤销可部署权限”和“删除仓库内容”。存在工作负载引用或进行中的部署时拒绝删除被引用版本。共享层的物理回收由仓库垃圾回收机制执行，API 删除不能承诺立刻释放指定磁盘空间。

### 4.3 分发

- 默认按需拉取：调度到节点后由运行时拉取，不全量广播到 64 台。
- 显式预热：指定 image_id 与节点范围；按节点报告 Pending/Pulling/Cached/Failed/Unknown。
- 预热优先采用专用、受控、仅用于拉取的 Kubernetes 工作负载；不能直接运行用户镜像默认入口作为“缓存动作”。实现前验证选定方式确实触发目标镜像拉取，并能核验 digest。
- 预热并发数有上限，区分认证失败、镜像不存在、网络超时和磁盘不足。
- 预热是当时的观察结果，节点缓存可能被回收；Cached 不构成永久驻留保证。
- 未就绪、被移出集群或不属于调用方范围的节点不能默认为预热成功。

## 5. 工作负载模型

第一版支持 service：持续运行的服务型负载，以 Deployment + Service 表达。job（运行至结束的任务）暂不开放，避免复用错误的停止和重试语义。

最小字段：名称、image_id、集群、受控命名空间、启动命令/参数、环境变量或凭据引用、副本数、CPU/内存/GPU、放置约束、端口、就绪/启动检查、退出宽限策略。

### 5.1 资源约束

- GPU（图形处理器）首版按整卡申请，数量为正整数；专用 CPU 验收环境可以配置 0 卡。
- 单 Pod（容器运行单元）只能运行在一个节点，其全部 GPU 需求必须由同一节点满足。
- 不把多副本等同于跨机联合计算；分布式作业另行设计。
- placement 指定资源池或允许节点范围，最终选择由调度器决定。默认不直接写 nodeName 绕过调度。
- 资源不足是 Pending/Unschedulable，不等于平台提交失败。
- 节点健康、可分配量、已申请量与实际利用率分别展示；低利用率不代表资源未分配。

### 5.2 启动与访问

生命周期：Accepted → Validating → Scheduling → Pulling → Starting → Ready；中途可能 Failed、Blocked 或 Unknown。

容器 Running 不等于服务 Ready。上游需提供协议相符的探针，或显式选择仅检查进程的较弱验收模式并在状态中标注。长启动过程使用启动检查，避免误判为进程故障而重启。

Service 默认只提供集群内地址。上游是否可直达 Pod/Service 网段待确认。外部访问由明确选定的基础设施出口实现，不在本项目内增加模型路由逻辑。返回地址时必须附带 scope=cluster/internal-network/external，不能把 ClusterIP 当作上游必然可达地址。

### 5.3 停止、更新与删除

- stop：service 期望副本设为 0，保留配置与版本。成功必须观察到目标资源真正停止，不能仅以提交修改成功作为结束。
- start：从停止状态按显式参数或保存的恢复副本数启动。
- scale：改变期望副本数，观察到指定 generation 的就绪结果后再完成操作。
- update：创建新的不可变 revision，更新 Deployment，观察滚动结果。镜像可用但资源无余量时可能无法平滑发布，必须报告原因。
- delete：删除平台拥有的工作负载资源，观察删除完成；不自动删除镜像、命名空间或共享资源。
- 节点/镜像等共享对象的修改不得由工作负载删除级联触发。

长连接归属于被部署应用。平台提供有上限的退出等待和状态，不承诺透明迁移会话；强制终止或绕过保护必须是独立授权动作。HTTP 管理接口本身采用异步任务，不要求上游保持长连接等待部署。

## 6. 节点管控

| 动作 | 实现边界 | 完成条件 |
|---|---|---|
| list/get | Kubernetes + 硬件资产关联 | 返回来源、观察时间、状态 |
| label | 受控标签前缀和允许值 | 观察目标标签值 |
| cordon | Kubernetes 设置不可调度 | 观察 unschedulable=true |
| uncordon | 恢复调度，先检查维护状态 | 观察 unschedulable=false |
| drain | 停止调度，按策略执行驱逐 | 可驱逐目标已迁出，例外明确列出 |
| reboot | 节点运维/带外适配器 | 重启信号及预期节点恢复均被核验 |
| join/retire | 集群自动化流程 | 成员关系、设备资源和资产记录一致 |

RBAC（基于角色的访问控制）分别限制查询、工作负载操作、节点维护和物理操作。节点管理权限与普通部署权限分离。

drain 必须处理 PodDisruptionBudget（工作负载中断预算）、DaemonSet、不可管理 Pod 和本地临时数据。默认不强制删除、不自动绕过预算；遇到阻碍报告 Blocked。不能把 drain 当作所有进程已退出或服务器可以立即断电的证明。

drain 失败后保留不可调度状态，明确告知上游；不会偷偷恢复调度。恢复由显式 uncordon 操作完成。reboot、power-off 等需在明确维护策略后开放；首版未实现的动作返回 capability_not_supported，不能伪报成功。

所有资源归属由认证上下文和服务端映射确定，不能信任请求体指定任意项目/命名空间。

| 方法与路径 | 含义 |
|---|---|
| POST /v1/image-uploads | 创建受限上传会话 |
| GET /v1/image-uploads/{id} | 上传会话状态 |
| POST /v1/image-uploads/{id}/complete | 发起仓库核验 |
| GET /v1/images | 分页查询可见镜像 |

| POST /v1/workloads | 创建 service |
| GET /v1/workloads | 分页查询工作负载 |
| GET /v1/workloads/{id} | 期望/实际状态、实例、访问方式 |
| POST /v1/workloads/{id}/start | 启动已停止服务 |
| POST /v1/workloads/{id}/stop | 停止但保留配置 |
| POST /v1/workloads/{id}/scale | 修改副本数 |

## 8. 异步执行与一致性

建议状态：Pending、Running、Blocked、Succeeded、Failed、Unknown。Blocked 可以继续协调；Unknown 表示依赖失联或结果不明，不能当作成功或自动补发非幂等动作。

- 所有变更支持 Idempotency-Key，键作用域为调用方 + 方法 + 规范化路径。相同键和相同规范化请求返回原 operation；不同请求返回 409。
- 数据库持久化操作后才向上游返回已接收。幂等保留期限纳入 API 契约；过期后的重试不能保证仍去重。
- 执行器使用租约、心跳和版本比较竞争任务，不依赖进程内队列作为唯一状态。
- Kubernetes 对象使用确定名称、所有权标签、UID 和目标 generation；超时后先查询再决定重试。
- 同一工作负载或节点的冲突操作串行化或返回 409，防止同时 stop/update 或 drain/uncordon。
- 用 List/Watch 同步状态，断线重连、资源版本过期时重新 List，并周期对账；状态附带观察时间。
- 服务进程重启后继续协调未完成任务；不能重复创建对象或重复执行重启。
- 跨数据库和 Kubernetes 无分布式事务。通过状态机和对账收敛；清理只作用于能验证所有权的对象。
- 超过观察期限不等于操作已取消。报告实际资源是否仍可能启动；停止/撤销必须另外执行并验证。
- 批量预热/节点操作逐项记录，允许部分成功，不能以批次一个布尔值掩盖失败节点。

## 9. 最小数据模型

| 实体 | 关键字段 |
|---|---|
| caller/project | 主体、权限、允许集群及命名空间映射 |
| cluster | 名称、API 地址、凭据引用、能力、健康、观察时间 |
| node | cluster_id、Kubernetes UID、资产标识、状态、标签、资源、观察时间 |
| gpu_inventory | node_id、设备 UUID、型号、健康来源与时间；无数据时 Unknown |
| registry | 地址、类型、凭据引用、项目映射 |
| image_upload | 主体、目标、到期时间、状态、确认操作 |
| image | 仓库、tag 快照、digest、平台架构、可用状态、引用关系 |
| distribution/item | 镜像、节点集合、每节点阶段、错误与观察时间 |
| workload/revision | 期望配置、镜像 digest、期望版本、停止前副本数、实际状态、拥有的对象 |
| operation | 幂等键、请求哈希、目标、阶段、租约、重试、错误、时间 |
| audit_event | 主体、请求标识、动作、目标、结果、脱敏变更摘要 |

数据库设置唯一约束保护幂等键和对象映射。密钥仅保存引用或加密值；日志与普通 GET 不返回原值。不要把镜像层或实时监测时序数据存进业务数据库。

### 9.1 接口执行边界

- 外部管理连接使用 TLS（传输层安全协议），校验对端证书；开发配置不得成为生产免认证默认值。
- 调用方不能指定任意集群地址、仓库地址或凭据内容来驱动后台网络请求；通过管理员注册的资源标识选择目标。
- 普通工作负载默认不允许 privileged、宿主机网络、宿主机路径挂载或挂载容器运行时 socket。GPU 支持由集群受控组件提供，不以开放宿主权限代替。
- 用户镜像是被执行的代码。限定允许仓库、资源和命名空间，不自动为其挂载平台 ServiceAccount 权限或平台密钥。
- 配置更新使用 revision/版本前提条件，出现并发修改返回冲突；不可覆盖上游未观察到的新状态。
- 操作审计至少记录谁、何时、对哪个对象、提交何种动作及最终结果。凭据与敏感参数只保留脱敏摘要。

## 10. 集群底座工作包

集群生命周期属于责任范围，分阶段交付，不因平台接口先实现而省略：

1. 盘点整机型号、每节点卡数、管理口、网络拓扑、存储、操作系统及现有配置。
2. 设计管理/业务/存储/计算网络、IP/DNS/NTP、证书和访问边界，验证地址不冲突。
3. 确定高可用控制平面、数据库与仓库部署位置、备份存储和恢复目标。
4. 锁定 Kubernetes、容器运行时、操作系统、驱动、CUDA、GPU Operator、固件的兼容基线。
5. 在试点节点验证设备发现、整卡申请、容器内 GPU 计算、探针和释放资源。
6. 分批纳管节点，每批执行镜像拉取与 GPU 验收，保留维护及回滚记录。
7. 编写控制平面/etcd、平台数据库、仓库内容及元数据的备份恢复方案，并进行隔离恢复演练。
8. 建立证书续期、驱动升级、节点排空、重启、退役的操作手册与自动化步骤。

DCGM（数据中心 GPU 管理工具）等监测组件可提供设备指标；Kubernetes 的 GPU 资源计数不能替代物理健康和实时利用率。具体采集组件按硬件和版本支持选择。

## 11. 独立项目建议结构

```text
gpu-cluster-platform/                # 暂定目录名，非已创建仓库
├─ api/                             # 控制器、认证、OpenAPI
├─ domain/                          # 业务对象、校验与状态机
├─ application/                     # 用例、幂等、操作编排
├─ adapters/kubernetes/
├─ adapters/registry/
├─ adapters/node-lifecycle/
├─ worker/                          # 租约执行、观察与对账
├─ persistence/                     # 数据库迁移、仓储
├─ deploy/                          # 本地验收与生产部署模板
├─ infra/                           # 集群安装/升级/恢复自动化
├─ tests/                           # 契约、集成、故障、验收
└─ docs/                            # 接口、运行手册和决策记录
```

可先用一个 Maven 项目中的包实现上述边界，无需一开始全拆成独立模块。真实适配器和开发测试替身严格区分；模拟成功不能计为集群验收通过。

## 12. 开发阶段与验收

### M0：接口与环境基线

- 固化范围、上传方式、工作负载类型、身份认证、访问网络及节点动作。
- 产出 OpenAPI 初稿、数据迁移、状态机、环境盘点和软件兼容表。
- 无真实设备时仍可开发接口骨架，环境结论不得猜测。

### M1：镜像上传闭环

- 上游标准推送 → 仓库核验 → image_id/digest 查询。
- 验证中断重试、无权限、digest 不符、仓库失联、重复 complete 和引用删除保护。

### M2：CPU 工作负载闭环

- service 创建、查询、stop/start、scale、revision、delete；实现异步与幂等。
- 在真实测试 Kubernetes 上拉取镜像、启动并观察探针、返回可达性范围明确的地址。
- 验证镜像不存在、拉取鉴权失败、进程失败、就绪失败、资源不足和 API 断连恢复。
- 平台进程重启后未完成操作能够收敛，同一幂等键不重复创建资源。

### M3：节点管控与分发

- 查询、标签、cordon/uncordon/drain，按节点记录镜像预热。
- 验证 drain 受保护阻塞、部分预热失败、节点离线、冲突动作与权限边界。

### M4：B300 试点与集群建设

- 真实 B300 节点的软件基线安装、设备纳管和整卡工作负载验证。
- GPU 请求数量与实际分配一致；容器内真实计算通过；停止后申请资源释放。
- 缺少驱动、设备不可用、显卡数量不足必须表现为可定位失败，不能回退为 CPU 成功。
- 物理维护适配器按已确认的带外接口实现，先在试点设备验收。

### M5：64 节点推广与交付

- 分批纳管 64 台/512 卡，核对资产、Kubernetes 资源与设备清单。
- 验证并发部署/拉取限速、失败恢复、控制平面及数据库/仓库恢复流程。
- 模拟节点维护与应用长连接，验证约定的排空期限和终止行为。
- 性能指标、可用性、恢复时间和数据丢失容忍度由业务确认后填写，不凭规模编造吞吐目标。

## 13. 第一轮编码的明确任务

在新的独立工作目录建立项目。第一轮完成：

1. Java 项目骨架、配置结构、数据库迁移及健康接口。
2. OpenAPI 与统一错误格式，operation/幂等请求的数据结构和状态转换。
3. Kubernetes/Registry 适配接口，明确真实与模拟配置。
4. 一个最小 service 创建与观察用例的契约测试；无环境时只报告模拟验证。
5. README 启动说明、未完成项和环境要求。

后续按 M1/M2 建立真实闭环，再进入 GPU/节点物理操作。不要先创建管理网页，也不要把 Token Factory 的计算线程池当成 Kubernetes 调度器。

## 14. 待确认清单与暂定处理

| 待确认 | 可先采用的开发边界 |
|---|---|
| 新项目路径、仓库名 | 等新页面指定；不自动复用 TF_Demo 远端 |
| 标准 push 还是 tar | 默认设计标准 push，tar 暂不实现 |
| 当前是裸机还是已有集群 | 接口可开发，真实适配验收等待环境事实 |
| 整机型号、网卡、带外管理、固件 | 不实施批量驱动/重启/装机 |
| 是否单机多卡还是跨机任务 | 首版单 Pod 单节点整卡，多个独立副本 |
| 长连接协议、维护等待、恢复能力 | 参数化有界退出，不承诺无损迁移 |
| 上游网络和服务访问方式 | 返回集群内范围，不声称上游可直达 |
| 认证提供方和租户隔离 | 接口预留主体映射，不在生产默认免鉴权 |
| 控制平面等额外通用资源 | 文档列资源需求，不默认占满 GPU 节点 |
| 并发、可用性、恢复目标 | 定义测量项，目标等待确认 |

## 15. 与旧项目的关系及授权边界

Mini Token Factory 可以打包为验收镜像，但它目前的回环监听需做容器部署适配，CUDA 路径必须在实际 B300 上验证。旧项目的 CUDA 编译成功不等于 B300 运行成功，不能照抄之前的示例 GPU 架构参数作为 B300 构建配置。

本说明暂存在 TF_Demo/docs/cluster-platform，仅用于交接；不是把新平台代码加入旧项目的决定。用户对 TF_Demo 的自动推送授权不自动扩展到尚未指定的新仓库。新页面应明确工作目录和远端后再同步。
