我要新建一个独立的 GPU 集群管理接口平台，项目不属于原有迷你 Token 工厂。

业务事实：64 台服务器、共 512 张 NVIDIA B300；上游通过接口上传镜像，由我方平台分发镜像、创建和运行容器工作负载，并执行节点管控。我方负责集群全生命周期。业务存在长连接，但协议和维护约束尚未确定。

只开发管理接口及后台执行能力，不需要前端、聊天、模型路由、推理负载均衡、Token 计费。镜像仓库、Kubernetes 和节点运行时负责底层执行，平台负责授权、校验、状态机和对账。

请以 PROJECT_SPEC.md 为开发基线：

- 建议 Java/Spring Boot + PostgreSQL，接入 Kubernetes 与 Harbor；具体版本需核对支持范围。
- 镜像默认采用标准 push，平台授权并核验 digest；大文件不经 Java 中转。
- 第一版支持 service 类型：创建、查询、启停、扩缩容、版本更新、删除；预热镜像与正式运行分开。
- 节点先实现查询、受控标签、cordon、uncordon、drain；物理重启/下电/装机需确认适配环境后开发。
- 基础设施变更返回 202 + operation_id；具备幂等、持久化任务、执行租约和重启恢复。
- 不能把 API 接受、Pod Running、镜像预热或 CUDA 编译成功分别当成部署就绪、永久缓存或真实 GPU 正确性通过。
- 默认不强制排空、不自动删除共享资源、不从管理接口执行任意宿主命令。

第一轮完成独立项目骨架、OpenAPI 初稿、数据库迁移、operation/幂等机制、适配接口及最小 service 创建观察用例。先用 CPU 测试集群验收，再在 B300 试点。无真实环境时明确标注模拟测试，不伪报落地。

先确认本页面的独立工作目录；如果没有提供，询问目录位置。新仓库名称和远端尚未授权，不得自动沿用 TF_Demo.git，也不要改动旧项目的计算代码。
